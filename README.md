# GigaAM UI Fixed

Почему эта версия отличается:
- ставит **актуальный GigaAM из GitHub**, а не старый `gigaam 0.1.0` с PyPI;
- использует Flask вместо Gradio;
- контейнер стартует без загрузки модели;
- есть индикаторы прогресса в UI.

## Важно

Официальный GitHub GigaAM уже содержит модели v3, включая `v3_e2e_rnnt`, а PyPI `gigaam 0.1.0` знает только модели до v2. Поэтому для v3 ставим пакет из GitHub.

## API для Windows Audio Recorder

1. `POST /api/transcribe` — multipart/form-data, поле `file` с MP3/WAV.
   Ответ: `{"job_id":"..."}`.
2. `GET /api/status/<job_id>` — опрос раз в секунду. Статусы: `queued`,
   `running`, `done`, `error`. При `done` полная расшифровка находится в
   `result.text`, фрагменты — в `result.segments`. При `error` причина в `message`.

Модель загружается лениво при первой задаче. Все задачи (включая UI и batch)
используют модель последовательно. Задачи хранятся в памяти: после перезапуска
сервера требуется повторная отправка. Отмена ожидания клиентом не отменяет задачу.
API не требует авторизации; используйте его в доверенной локальной сети.

Для запуска: `docker compose up -d --build` (Docker с NVIDIA GPU).
Для разработки вне контейнера путь данных задаётся `GIGAAM_DATA_ROOT`.

### Основной результат SRT

`result.primary_format` равен `srt`, файл доступен по
`/download/<result.files.srt>`. Windows Audio Recorder автоматически отправляет
запись после остановки, ожидает `done` и сохраняет полученный SRT в папке встречи
рядом с MP3. UI сервера автоматически передаёт SRT браузеру для скачивания.
Имена серверных результатов включают job_id для предотвращения коллизий.
Тайминги относительно начала аудио: сегменты модели, если доступны, иначе границы
фрагментов (20 секунд по умолчанию; короткие записи — один интервал).
Проверка сериализации и смещения таймингов: `python -B -m unittest test_subtitles`.
После изменения исходников контейнер требуется пересобрать.

После сохранения SRT и TXT клиент вызывает `DELETE /api/jobs/<job_id>`:
удаляются входное аудио, результаты и статус только этой задачи. Другие встречи
и кэш весов модели не затрагиваются. Очистка идемпотентна; активная задача
возвращает 409. При ошибке сохранения клиент не запрашивает очистку.
При ошибке очистки локальный SRT остаётся доступным, интерфейс показывает ошибку.
В веб-интерфейсе SRT автоматически передаётся браузеру для скачивания, затем
данные задачи удаляются и поля страницы очищаются. Проверьте настройки загрузок
браузера. Тайминги по фрагментам 20 секунд приняты для этого сценария.

### Быстрое обновление существующего CUDA-образа

`docker tag giga-gigaam-ui gigaam-ui:runtime-base`

`docker build -f Dockerfile.update -t giga-gigaam-ui:meetings-1.1.0 .`

`Dockerfile.update` использует установленное окружение без повторной загрузки
CUDA/PyTorch. Для новой машины используйте основной `Dockerfile`.
На текущей машине переопределение `docker-compose.local.yml` сохраняет
`C:/Dev/giga/data` и внешний том `giga_gigaam_hf_cache`; файл исключён из Git.
Запуск обновления: `docker compose -p giga -f docker-compose.yml -f docker-compose.local.yml up -d --no-build`.

### Веб-интерфейс записей

Веб-страница поддерживает выбор нескольких аудио- и видеофайлов, изменение порядка,
последовательную обработку отмеченных записей и просмотр результатов TXT/JSON/SRT.
Пакет UI использует существующие POST /api/transcribe и GET /api/status/<job_id>:
контракт API для Windows Audio Recorder не меняется. Веб-страница не вызывает
автоматическое удаление задачи после скачивания, поэтому результаты остаются
доступными до очистки. Описанное выше автоматическое удаление относится к клиенту
Windows Audio Recorder, а не к обновлённой веб-странице.

Кнопки «Очистить outputs», «Очистить logs» и «Очистить HF cache» сохранены.
Очистка требует подтверждения. Консоль показывает события текущей страницы;
это не поток docker logs. Очередь и история страницы не сохраняются после перезагрузки.
Видео обрабатывается через FFmpeg: поддержка конкретного контейнера зависит от FFmpeg.
Для проверки своей речи откройте http://localhost:8000 и загрузите запись голоса.

Предел загрузки по умолчанию — 5120 МиБ (5 ГиБ) на HTTP-запрос.
Его можно изменить переменной MAX_FILE_MB; веб-очередь отправляет каждый файл отдельно.

Очистка inputs удаляет загруженные записи; общая очистка inputs и outputs также удаляет результаты и историю заданий. При активном распознавании очистка возвращает HTTP 409.

### Intel Mac: локальный запуск на CPU

Нужен Docker Desktop для Intel Mac (работающий Docker Engine).
Из каталога проекта выполните:

```bash
docker compose -p gigaam-cpu -f docker-compose.cpu.yml up -d --build
```

Откройте http://localhost:8000. Это самостоятельная конфигурация: не объединяйте
её с docker-compose.yml или docker-compose.local.yml, требующими Nvidia.
CPU-образ содержит CPU-версии PyTorch и torchaudio; GigaAM закреплён на конкретном
коммите. Интерфейс, API и лимит 5 ГиБ сохраняются. Первая задача скачивает модель,
поэтому для неё нужен интернет. Кэш модели сохраняется в отдельном Docker-томе;
записи и результаты находятся в ./data. После загрузки весов проверьте автономную
работу на своей записи. Скорость зависит от CPU и выделенных Docker ресурсов.
Если Docker сообщает о нехватке памяти, увеличьте его лимит в настройках Resources.
Не запускайте GPU- и CPU-конфигурации одновременно с одним каталогом ./data.

```bash
# Журнал сервиса
docker compose -p gigaam-cpu -f docker-compose.cpu.yml logs -f
# Остановка без удаления модели и результатов
docker compose -p gigaam-cpu -f docker-compose.cpu.yml down
```

На Intel Mac аппаратная скорость пока не проверена. Запись длительностью 5–10 минут
подойдёт для измерения времени обработки. Для обновления используйте ту же команду
up -d --build после получения новой версии исходников.
